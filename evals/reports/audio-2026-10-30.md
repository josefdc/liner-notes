# Audio accuracy, 2026-10-30

The audio service (`services/audio`): its answers on generated controls, measured by `evals/audio` (`uv run python -m evals_audio`). The harness imports the service and calls its own `analyze_signals`, so the numbers are what the service returns, gate and withholding rules included. Rendered from `audio-2026-10-30.json`, which holds the per-clip results: track ids, estimates and scores. It stores no reference labels and no audio file names, but an estimate with its score often gives the reference away, so those results are derived from the annotations: the licence and credits under each dataset apply to them. Not run for this report: tempo on Ballroom (ISMIR 2004 tempo induction contest); tempo on GiantSteps Tempo; key on GiantSteps Key, as GiantSteps+ (Faraldo 2017 revision); what the tempo rules compare on Ballroom (ISMIR 2004 tempo induction contest); what the tempo rules compare on GiantSteps Tempo; what the key rules compare on GiantSteps Key, as GiantSteps+ (Faraldo 2017 revision); the golden set; the estimators' costs. Any report in `evals/reports` that holds them states the analyzer version it was made with.

Runs in this report: the generated controls (librosa, essentia, beat-this). beat-this is measured here only: the service does not ship it, and the service's default estimator is not changed by this report.

## How to read it

- **n** is every selected clip with verified audio and a usable reference. **Answered** clips got a value from the service; **withheld** clips got none; **failed** clips raised an error (none is expected). Coverage is answered / n.
- **correct / n** counts a withheld clip as no correct value. It answers *how often does a user get a right value*. **correct / answered** is the share of returned values that are right. It answers *how often is a value the service shows right*, and it depends on which clips the service chose to answer: two estimators that answer different clips are compared in the paired table, not by this column.
- **Intervals** are 95 %: Wilson score intervals for Acc1, Acc2 and exact; a BCa bootstrap (10,000 resamples, fixed seed) for MIREX, with no interval when every score is equal. Each interval rests on the denominator printed next to it, which for correct / answered can be far below n.
- **p-values** are exact where it is cheap (McNemar; sign-flip; the AUC's permutation test up to 200,000 orderings) and Monte Carlo at a fixed seed otherwise, as labelled, computed as (hits + 1) / (resamples + 1). Each is for one comparison. This report gives 0 distinct ones (the default-estimator table repeats some of them); about 0.0 of them are expected under 0.05 by chance alone, so none should be read as a finding without a correction for the number of tests.
- **beat-this** (checkpoint `final0`, CPU, no DBN) is not part of the service; the harness runs it behind the service's estimator interface, so its tempo goes through the service's own rules: the onset-periodicity minimum, 40-208 BPM, the tempo refined from the beats on onsets, and the steadiness check. It gives no confidence (so no curve and no confidence minimum) and no key. Its authors trained `final0` on every dataset they used except GTZAN, Ballroom included: an estimator marked *trained on this dataset* is shown on its own training data: those cells are not evidence about new music and its pair tables there are not printed.
- **Comparability**: one 30 s window per clip and the excluded labels make these numbers incomparable with published figures for the same datasets (computed on full excerpts, usually on every labelled track).

## Reproducing

Datasets are fetched into `~/liner-notes-data` (or `LINER_NOTES_DATA`), outside the repository, under a cap (`LINER_NOTES_DATA_CAP_BYTES`, 2 GB by default). Only the selected tracks' audio is written, each checked against mirdata's MD5. See `evals/audio/README.md`.
